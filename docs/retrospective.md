## CLAUDE.md는 어떻게 자랐나

ch2에서는 프로젝트 개요, 기술 스택, GCP 환경, 행동 규칙 세 줄로 시작했다. ch3에서 배포 원칙
세 줄이 붙었다. 클러스터를 직접 고치지 않는다, 이미지 태그는 CI가 SHA로 갱신한다, 올린 태그는
덮어쓰지 않는다. 세 줄 모두 그 장에서 실제로 사고가 날 뻔한 지점에서 나왔다. ch4 이후로는
저장소 구조가 늘 때마다 갱신됐다.

규칙이 미리 정해져서 내려온 게 아니라, 겪은 일이 규칙이 됐다. ch2에서 같은 태그로 이미지를
다시 빌드했다가 노드 캐시 때문에 이전 코드가 계속 돌았던 일이 "태그를 덮어쓰지 않는다"로
남았다.

## 반복해서 나타난 선택 기준

16건의 결정을 늘어놓고 보면 같은 기준이 반복된다.

**관리형을 먼저 본다.** Gateway API는 GKE가 관리하는 로드밸런서에 직접 붙어 Controller Pod을
띄우지 않는다(ADR-006). 시크릿도 Vault를 세우는 대신 Google Secret Manager와 GKE managed
CSI를 썼다(ADR-009). 학습 환경에서 운영 부담을 줄이면서 클라우드 네이티브 방식을 익히는
쪽을 골랐다.

**같은 생태계로 묶는다.** ArgoCD와 Argo Rollouts는 같은 argoproj다(ADR-001, ADR-007).
Blue/Green에서 Canary로 넘어갈 때 Rollout 리소스와 GitOps 흐름을 그대로 두고 전략만
바꿀 수 있었던 이유가 여기 있다(ADR-010).

**Grafana 한 화면으로 모은다.** Prometheus, Loki, Tempo를 모두 Grafana 데이터소스로
붙였다(ADR-003, ADR-004, ADR-015). 메트릭에서 이상을 보고, 같은 화면에서 로그로 넘어가고,
다시 트레이스로 들어가는 흐름이 끊기지 않는다. Jaeger나 Kibana를 썼다면 창을 옮겨 다녀야
했다.

**UI 설정보다 Git에 남기는 쪽을 고른다.** 알림에서 이 기준이 가장 선명하게 드러났다.
Grafana Alerting이 처음 설정은 훨씬 빠르지만 규칙이 Grafana 데이터베이스에만 남는다.
PrometheusRule은 YAML로 Git에 남아서 PR 리뷰를 거치고 `git blame`으로 "이 임계값이 왜
5분인지" 답할 수 있다(ADR-005). 같은 이유로 결정 자체도 ADR로 저장소에 남겼다.

## 자원 압박이 가장 큰 제약이었다

책의 예산표는 e2-medium 2노드를 3200m으로 잡았지만 실제 allocatable은 노드당 949m,
합계 1880m이었다. GKE 시스템 구성 요소가 그중 상당 부분을 이미 쓰고 있었다.

ch4에서 관측 스택을 올린 뒤 85%에 닿았고, ch6에서 Secret Manager CSI DaemonSet이
노드당 120m을 더 가져가면서 100%에 도달해 Valkey가 Pending에 걸렸다. 두 번 대응했다.
먼저 관측 스택의 requests를 줄였고(Prometheus 100m → 25m 등), 그래도 부족해서 GKE 관리형
로깅과 모니터링 에이전트를 껐다. Loki와 Prometheus를 직접 운영하기로 이미 결정했으니
(ADR-003, ADR-004) 중복이었고, 노드당 약 130m을 돌려받았다.

ch7에서 노드풀을 나누고 나서야 여유가 생겼다. 역할별 분리가 격리뿐 아니라 자원 문제의
해법이기도 했다는 점이 ADR-011에 기록돼 있다.

## 다시 한다면 다르게 볼 지점

**시크릿을 GCP에 묶은 것.** GKE managed CSI는 설정이 간단하고 키 파일이 없다는 장점이
분명하지만 GCP에 종속된다. 다른 클라우드로 옮기거나 멀티 클라우드를 고려한다면
Sealed Secrets나 External Secrets Operator가 중립적이다. 대신 키 회전을 직접 관리해야 한다.

**Canary를 6장까지 미룬 것.** Blue/Green을 5장에서 하고 Canary를 6장에서 했는데, 그 사이에
Valkey와 Secret이 들어오면서 자원이 빠듯해져 replicas를 1로 줄여야 했다. 결과적으로 Canary
단계별 트래픽 분배를 여러 Pod으로 보여주지 못했다. 노드풀을 먼저 나누고 Canary를 했다면
시연이 더 선명했을 것이다.

**Kafka를 8장에 둔 것.** ID 발급과 알림 발송을 처음부터 분리했다면 Valkey를 도입할 때
Redis Streams로 두 가지를 한 컴포넌트에 묶는 선택지도 검토할 수 있었다. 지금 구조는 Valkey와
Kafka를 둘 다 운영한다. 규모가 작을 때는 하나로 줄이는 편이 나을 수 있다.

## 겪은 문제의 성격

15건의 트러블슈팅 기록을 분류하면 이렇다.

- **권한과 정책** 3건: 새 GCP 프로젝트의 Cloud Build 권한, 조직의 워크플로 쓰기 권한, Workload Identity 노드풀 적용
- **차트 기본값과 실제 환경의 불일치** 5건: Loki의 읽기 전용 루트, GKE의 coredns 부재, Strimzi의 nodeSelector 미지원 등
- **자원 부족** 3건
- **비동기 동작의 타이밍** 4건: GatewayClass 생성 지연, proxy-only 서브넷, ArgoCD 3분 재조정, NEG 재등록

절반 이상이 "문서에 적힌 대로 했는데 이 환경에서는 다르게 동작한다"였다. 가드레일이 있어도
버전이 올라가면 어긋난다. Strimzi가 0.51에서 1.1로 올라가며 Kafka 4.1 지원이 사라지고
KafkaNodePool이 필수가 된 것이 대표적이다. 그래서 겪은 것을 그때그때 `JOURNEY.md`에
남기는 편이 다음 번에 값을 한다.

## Git, AI, Ops가 만나는 지점

세 요소가 각각 무엇을 맡았는지 정리하면 이렇다.

- **Git** — 코드와 매니페스트뿐 아니라 결정(ADR), 진행 이력(JOURNEY.md), 현재 구조
  (claude-context), 위험 작업 절차(command-guardrails)까지 담는다
- **AI** — 매니페스트를 쓰고 오류를 진단하지만, 그 결과를 저장소에 문서로 되돌려 놓는다
- **Ops** — ArgoCD가 Git 상태를 클러스터에 반영한다. 사람도 AI도 클러스터를 직접 고치지 않는다

한 바퀴가 다음 바퀴를 짧게 만든다. ch3에서 ArgoCD를 고를 때는 대안 비교가 필요했지만, ch7에서
App of Apps를 도입할 때는 ADR-001이 이미 "ArgoCD를 쓰고 확장은 App of Apps로 간다"고 적어둬서
곧장 실행으로 갈 수 있었다. ch6에서 Canary로 넘어갈 때도 ADR-007이 "6장에서 Canary로 넘어갈
여지를 남긴다"고 써 있어서 전제를 다시 세울 필요가 없었다.

기록이 다음 결정의 입력이 되는 구조. 그게 이 저장소가 보여주려는 것이다.

## 다음에 할 만한 것

**보안.** 지금은 네임스페이스가 나뉘어 있을 뿐 트래픽은 자유롭게 오간다. NetworkPolicy로
테넌트 간 통신을 막고, RBAC을 ServiceAccount 단위로 좁히고, Kyverno나 OPA Gatekeeper로
정책을 강제하는 순서가 자연스럽다.

**스케일링.** HPA를 붙여 요청량에 따라 Pod을 늘린다. Kafka Consumer는 큐 길이 기반이
맞으므로 KEDA를 검토한다. 노드는 Cluster Autoscaler로 자동 확장한다.

**비용.** 지금 5노드가 모두 Spot이다. 안정성이 필요한 워크로드(Valkey, ArgoCD)는 일반 VM으로
옮기고 나머지는 Spot을 유지하는 식으로 나눈다. requests를 실제 사용량 기준으로 다시 잡는다.

**관측 심화.** SLO와 SLI를 정하고 Burn Rate 알림으로 바꾼다. 지금 알림은 "Pod이 재시작했다"
수준이라 사용자 영향과 연결되지 않는다. 트레이스도 전량 샘플링이라 규모가 커지면 조정이
필요하다.

**멀티 리전.** 지금은 단일 존이다. Spot VM이 회수되면 노드가 사라진다. 리전 클러스터로
바꾸거나 다른 리전에 클러스터를 하나 더 두고 ApplicationSet으로 함께 관리한다.
